6. TRAVESSIA: DIVERGÊNCIA ENTRE AS REGRAS
No JSON recebido, o núcleo define TEMPO_PADRAO=15 e TEMPO_PCD_IDOSO=28; isto representa duração total da travessia, com diferença de 13 s para perfis, e não um campo de extensão solicitado pelo usuário. O núcleo aceita quando o verde dos carros tem mais de 8 s; caso contrário registra RECUSADA e manda pedir novamente.
O front-end local tem controlador próprio, adicional explícito de 0 a 15 s e possibilidade de reservar outro ciclo. O fluxo recebido não contém confirmação de abertura, fim ou reserva do próximo ciclo. Portanto, o painel integrado apresenta ACEITA/RECUSADA e os tempos gravados, sem marcar uma travessia como aberta ou concluída.
Não limitar NR_TEMPO_CONCEDIDO a 15: isso confundiria duração total com extensão.
Para compatibilizar uma extensão explícita, modificar a função tempoDoPerfil no mesmo núcleo e a função travessia somente depois de definir de onde vem o adicional. A fórmula deverá ser TEMPO_BASE + Math.min(15, Math.max(0, adicional)), com números inteiros validados. A regra atual de perfis, 15/28, já mantém uma diferença de 13 s, mas não oferece escolha de 0 a 15.
Aguardar o próximo ciclo ainda NÃO é uma funcionalidade do backend. Implementá-la exige um estado de reserva, timestamps de abertura/fim e confirmação do simulador. Não basta trocar a mensagem “RECUSADA” por “Aguardando”. O simulador Python não foi fornecido; não há como fornecer um encaixe fiel de callbacks sem esse contrato. Preservamos a simulação local e registramos essa dependência, sem criar estados fictícios.
No núcleo, mudar o texto de autorização para deixar explícito que é uma simulação acadêmica e que a resposta do bot não autoriza atravessar uma via real.

7. FORMULÁRIOS: ROTA ESTRUTURADA A CRIAR
Nenhum POST /api/chamados existe no fluxo fornecido. Os formulários continuam locais; o chat real não depende desta etapa.
Para criar uma rota de registro sem interpretar mensagens, definir primeiro no Node-RED o contrato:
- tipo: TRAVESSIA, APOIO_METRO ou ZELADORIA;
- session: sessão WEB do cidadão;
- idRequisicao: UUID estável por tentativa, para evitar duplicação em reenvio;
- metro: estacao_id do catálogo do servidor, ponto_encontro e descricao;
- zeladoria: local_livre e descricao;
- travessia: cruzamento_id e adicional de 0 a 15, com decisão exclusiva do controlador;
- nunca CPF, RG, PIN ou documentos.
Conexão necessária: http in “POST /api/chamados” -> function “Validar pedido estruturado IARA” -> consulta dos IDs de estação/cruzamento no SQLite -> function de regras do serviço -> SQLite de INSERT com RETURNING -> function de resposta {ok:true,chamado:{...campos da consulta individual...}} -> http response.
A gravação deve usar o cidadão autenticado, validar IDs existentes e aplicar idempotência; não aceitar nomes de linha ou instituição enviados pelo navegador como permissão. A rota administrativa de decisão não serve para registrar novos pedidos.
Para esta etapa não há código de backend acrescentado ao repositório nem uma rota fictícia habilitada no front-end. Como a travessia externa e a autenticação ainda não têm contrato de reserva/identidade, ativar essa rota agora com uma cópia do simulador local produziria duas fontes de verdade. Primeiro concluir os passos 2 a 6, validar o contrato externo e então adaptar os três submits do app.js para essa rota real.

A etapa seguinte, após essa rota existir e ser validada, é trocar os submits de apoio e zeladoria em app.js por fetch estruturado, usando a mesma session de buscarSessaoIara(), um idRequisicao mantido para reenvios da mesma tentativa e o chamado retornado como resultado. Não ativamos essas chamadas antes de existir uma rota real.

7.2 CONSULTA ADMINISTRATIVA SEM LIMITE SILENCIOSO
O nó “Montar consulta” de ID 39899e075722d1bb termina o SQL com LIMIT 200. Isso restringe a quantidade que os painéis conseguem receber. Para mostrar todos os registros na demonstração local, substituir apenas:
' ORDER BY l.DH_SOLICITACAO DESC LIMIT 200'
por:
' ORDER BY l.DH_SOLICITACAO DESC, l.ID_SOLICITACAO DESC'
Para volume de produção, será necessária paginação autenticada, em vez de transferir toda a tabela a cada 3 segundos.

8. PERMISSÕES E EXPOSIÇÃO
No fluxo recebido, /api/chamados e /api/chamados/:id/decisao não verificam o usuário autenticado nem o vínculo de estação. As verificações do front-end organizam a interface, mas não protegem a API.
Manter Node-RED acessível somente em loopback durante a demonstração, sem túnel público ou redirecionamento de porta. Em settings.js, revisar uiHost: '127.0.0.1'.
Antes de acesso por rede, configurar HTTPS e autenticação das rotas HTTP por httpNodeMiddleware/httpNodeAuth, conforme a documentação oficial. Não inserir senha de API, token Groq ou Telegram no JavaScript do site.
No middleware de produção, associar a conta autenticada à função, instituição, linha e estação em dados do servidor. O GET deve filtrar esses vínculos em SQL; o POST deve validar novamente o mesmo vínculo antes do UPDATE. A sessão administrativa atual do protótipo é local e não pode ser usada como prova de identidade.
A consulta antiga não devolve linha/instituição. A interface valida estação e catálogo da linha do operador sem atribuir linha fictícia ao pedido. Para distinguir instituições em estações compartilhadas, acrescentar à consulta os campos orgao e linha a partir dos relacionamentos reais do seu banco. O schema desses relacionamentos não consta no JSON, portanto não foi inventado um JOIN ou uma coluna.
Se o servidor passar a usar cookie de sessão: configurar CORS com origem exata e Access-Control-Allow-Credentials: true; somente então mudar configuracaoIara.credenciais para 'include'. A API local atual não anuncia essa permissão; 'omit' permite o chat atual sem cookies.

9. VALIDAÇÃO APÓS CADA ALTERAÇÃO
Chat: enviar menu, selecionar uma opção e conferir continuidade da session.
Gravação: conferir registro no GET; simular erro de SQLite e confirmar que o cidadão não recebe sucesso.
Metrô: aprovar/recusar somente um pedido fictício de teste; conferir status no GET e notificação no poll. Clicar novamente deve receber 409, sem segunda notificação.
Privacidade: criar duas sessões fictícias; /api/meus-chamados deve retornar somente os pedidos da sessão correta. Parâmetro inválido deve falhar. Em produção, sessão de outro usuário deve receber 403 pelo middleware.
Painéis: verificar atualização em aproximadamente 3 s; desligar Node-RED e conferir que os últimos registros continuam visíveis.
Travessia: comparar tempos persistidos com os do controlador; não apresentar tempo_concedido como adicional.
Formulários: manter a identificação de simulação local até existir uma rota estruturada testada.
